# Reply flags and dropped drafts

[#61](https://github.com/Singh-Mehtab/learnharness-anki-bridge/issues/61) exposed two problems: one flag on a long reply can request cards about every extracted idea, and the same request is selected on every visit even after the user has reviewed its drafts.

## What the flag asks for

- Keep the reply's message IDs as the anchor. Extracted ideas matched by provenance are candidates. A flag can exist before the ideas do.
- A blank note keeps the current behavior: request at least one card per matched idea, subject to the existing rules for unsupported ideas and repeated recall tasks.
- With a note, send the note once with the selected candidates from that reply. The writer chooses which candidates answer the request. A candidate selected only because of the note does not have a card minimum. It can use the flagged cap for distinct cards the note asks for. Ignore unrelated candidates. If the user separately selects an idea for ordinary writing, it remains an ordinary target even if it is also a candidate.
- Keep one noted request together in a worker input. Respect preflight limits and show a skip if the group cannot fit; do not silently turn it into separate requests that could each fulfil the same note. Do not add a model call for classifying ideas or use keyword matching. A note stays data, subject to the built-in writer rules. Overlapping notes stay together when batching. If the group cannot fit, ideas selected on their own can still be written without that note.
- In Make cards, group candidates under their flag, showing the note and candidate count. Let the learner include or exclude a group before estimating. Ideas shared by flags still use one node ID and are written once per worker input.

## When a flag has been handled

- Update handled state when the worker result and drafts are saved, before sending anything to Anki. For a noted flag, the writer identifies which notes its cards answer. Saving at least one such card, or finding an exact duplicate draft, handles the candidates sent with that note. Candidates that weren't sent or whose statements changed stay pending. For a blank flag, track the matched ideas that got drafts so failure, partial selection or newly extracted ideas do not resolve the rest.
- Failed, cancelled or skipped work does not handle a flag on its own. Editing a note renews the request. A late result from an older note must not handle the edited flag. Recovering an interrupted save follows the same rules as the initial save.
- Keep handled flags visible and manually selectable. Do not tick their handled requests by default, even after their cards are dropped. Do not infer past intent from unrelated historical cards.

## Dropping a draft

Drop affects only the draft. If a single-card Drop removes the last draft and the idea has no applicable cards left, offer **Don't make cards for this idea** using the existing statement-scoped dismissal. Without that choice, the idea still shows as **No cards** and is eligible for manual selection and **Select ideas without cards**. Dropping one draft must not dismiss sibling drafts or remove a reply flag.

The separate **Regenerate this card** idea is for later: ask for a replacement for one unsent draft, optionally with a short instruction, and let the user review the replacement before discarding the original. It is not part of #61.

## Checks

Use synthetic replies. Cover a long reply with a narrow note, a blank flag, overlapping candidates, manual selection and model limits. Check that repeat visits do not preselect handled requests, and cover partial and failed results, note edits during a run, and saved-result recovery. Exercise Drop with and without a dismissal and check that other drafts are unaffected. Verify the UI and worker input without using real study data or the user's Anki profile.
