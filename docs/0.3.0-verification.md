# 0.3.0 verification

Checked on 2026-11-18 against LearnHarness 0.6.1 (plugin API v1). This records what was tested, how, and what wasn't.

## Automated tests

`npm test` runs 97 tests. Typecheck and build pass. No test calls a model or Anki.

The generation backend tests run against a fake host. It stands in for the graph, the model catalog and the worker service, and its worker records survive plugin restarts the way host history does. The tests cover:

- Preflight refuses to run without an explicit model, when the selected model or its provider key is missing, and on duplicate or missing node IDs. Estimating never starts a worker.
- Confirmation re-runs the preflight and compares a digest of the exact prompts, limits, skips, model entry and source statements. A changed setting or node statement makes it stale. A hand-written card does not, since it never enters a prompt.
- A confirmed generation calls the worker with purpose `user`, 3 turns, a three-minute timeout and the preflight's output allowance. Repeating the confirmation is a no-op.
- Valid results become `draft` cards with a frozen source snapshot. Writer skip reasons are kept. Invalid results fail the task and create nothing.
- Cancel stops unfinished tasks. A late success after cancel never becomes a draft.
- On restart, a result that finished while the plugin was off is applied once. A dropped draft is not recreated on the next restart. Unfinished tasks become `interrupted`, and activation never starts model work. Recovery also works when acceptance was saved before the worker task ID.
- A crash between cancel's task and batch saves still recovers as `cancelled`. An unexpected driver failure marks the batch `interrupted` instead of leaving it `running`, which would block new generations.
- Schema 1 state migrates to schema 2 without losing pairing or cards. Malformed generation data is refused and left on disk unchanged. Persisted results get a shape check only, so a stricter future writer rule can't lock an old state file.

Frontend tests (happy-dom) cover the drafting panel and the review list:

- Generation needs a node selection, a model and a confirmed estimate. Changing the selection discards the visible estimate.
- Polling a running generation rebuilds neither the pickers nor the settings, and unsaved cap and kind edits survive. Clicks made while an action is running are queued, not dropped.
- A background refresh after new drafts arrive keeps half-typed hand-written cards, open sections, unsaved review edits and the caret. A refresh that arrives during a dialog runs once the dialog closes.
- The source statement and preview render as text or host markdown, never raw HTML. Bulk approval refuses unsaved editor content and needs a confirmation dialog. Dropped cards are excluded from bulk send.

## Scratch LearnHarness run

I ran the built plugin in a LearnHarness 0.6.1 checkout. It used scratch `LH_DATA_DIR` and `LH_AUTH_FILE` paths, a sanitized environment and headless Chromium through Playwright. The graph held two synthetic nodes, Boyle's and Charles's laws.

The model was a local OpenAI-compatible stub registered as a keyless custom endpoint through LearnHarness's own `/api/custom-provider` route. It returns fixed cards through `submit_result`, and those cards were first checked against the real writer validator. Nothing reached a real model, and no user credentials were involved.

End-to-end, all passing with no page errors:

1. The native knowledge picker selected both nodes. The plugin listed their statements.
2. The native model picker set `custom / stub-writer`. No request reached the stub.
3. The estimate read "2 nodes, up to 4 cards in 1 model call", 1835 input tokens, 1600 reserved output tokens and no dollar estimate (the endpoint is unpriced). Still no request reached the stub.
4. Confirming produced exactly one stub request, with `max_tokens` 1600, matching the estimate. Two drafts arrived with source snapshots, and the saved state was schema 2.
5. Review showed each source statement beside its editor. The preview rendered the inline maths and a fenced Python block.
6. Editing and saving one card worked. Bulk approval opened a confirmation dialog. Afterwards both cards were `approved` with no Anki note ID. The request log can't show the absence of a send, because every plugin RPC posts to the same path, so the saved state is the evidence here.
7. Disabling and re-enabling the plugin left `state.json` byte-identical, and no new model request was made.

Host restart during generation, with the stub delaying its reply by 60 seconds:

1. The batch was saved as `running` before the host was killed.
2. After restart, the batch showed as `interrupted` and the existing cards were unchanged.
3. Activation sent no new model request.
4. "Estimate retry" produced a fresh estimate without calling the model.

## Not verified

- **A real model.** The stub proves the plumbing, the token allowance and the result handling. It says nothing about card quality from a real model inside the app. The 0.1.x bench evidence still stands, and the user's Claude subscription would pay for any real run.
- **Sending generated cards to Anki.** Delivery code is unchanged from 0.2.0 apart from the new drop operation. The 0.2.0 live AnkiConnect checks still apply, but generated cards were not sent to a throwaway profile in this run.
- **Source-change and missing-node flags in the app.** The backend tests cover them. The scratch graph ledger is append-only and the first line defines a node, so the run did not edit a statement.
- **Packaged Electron app.** Only the Next.js dev server was used.
- **Large graphs.** Batching across several model calls is covered by unit tests, not the scratch run.
- **Concurrent windows.** Two views of the plugin open at once are expected to work through the shared backend fence, but this was not exercised.

The run also surfaced a Next.js security notice for the reference checkout's Next 16.4.3. It doesn't affect the plugin, which ships no Next.js code.
