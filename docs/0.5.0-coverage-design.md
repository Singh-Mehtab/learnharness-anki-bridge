# Coverage design for 0.5.0

Status: proposed specification for review, with graph identity behavior tested on LearnHarness v0.6.1. No 0.5.0 plugin behavior is implemented by this change.

The user chose to wait for 0.4.0 before coding coverage. PR #4 is now merged; its schema 3 and final session contracts are the implementation baseline. This design does not authorize implementation. The version numbers below describe milestones, not permission to start the next one.

## Scope

Show coverage beside source nodes in the session draft list and the graph-wide manual picker. Add a "No cards" filter and a bulk selection action to the picker. Backfill uses the existing estimate, model confirmation, review and send flow. It has no separate generation or delivery pipeline.

Add an explicit, reversible "Don't card this" choice. Keep delivery history intact. Never update, delete or recreate Anki notes in response to coverage changes.

## Identity and source changes

Use exact IDs from `ctx.learning.graph().propositions`, as manual generation does in 0.3.0. A proposition seen in multiple sessions shares one coverage record. The graph's implication nodes and arrows provide writer context but are not selectable generation targets.

The [scratch identity experiment](0.5.0-graph-identity.md) passed 14 cases, including an independent rerun. Reencounters keep the existing ID and add phrasings and provenance. Aliases are text, not old-ID redirects. Do not match coverage by alias, name, statement text or semantic similarity. A deleted and recreated proposition has a new ID and starts without coverage. Keep the old card history under its missing ID.

Use the existing SHA-256 hash of the exact UTF-8 statement, without normalization. Compare generated cards against their saved source snapshot. Later aliases, provenance, names, chains or source-passage changes do not change this hash. Coverage is a statement-level reminder, not a claim that every angle of an idea is covered. The existing generation preflight still binds the actual writer input.

When the graph facade reports a read failure, keep the last view marked stale, disable selection-changing actions and ask for a refresh. Do not label every source missing or write state from that failed call. LearnHarness v0.6.1 can also silently return empty or partial data: its store catches ledger read errors and skips corrupt or invalid lines, and API v1 supplies no completeness flag. "Source missing" therefore means absent from the returned proposition snapshot, not confirmed deletion. Keep history intact and describe that uncertainty; do not infer a healthy ledger from a successful call.

## Card counts

Derive counts from the saved cards and paired destination on every snapshot. Do not store a second coverage ledger.

| Saved card condition | Contribution |
|---|---|
| `draft`, `approved` or `failed`, without a note ID | One waiting card. A definite delivery failure still needs a user decision. |
| `sending` | One waiting card with an unresolved-delivery warning. Reconcile it before generating more cards for that node. Never infer success or failure from coverage. |
| `sent` with a valid note ID and the same normalized URL and profile as the saved pairing | One sent card, regardless of deck. |
| `sent` to another destination, or no destination currently paired | One sent-elsewhere card. It does not cover this destination. |
| `dropped` | No coverage. Keep its history. |

Use the existing destination comparison. Do not equate `localhost` with `127.0.0.1` or infer that different URLs serve the same collection. Changing decks does not change coverage. Changing the pairing recomputes sent and sent-elsewhere counts without rewriting cards. A configured URL that no longer matches the saved pairing shows a pairing warning; changing settings alone does not silently re-pair.

A presence check that reports "deleted in Anki" does not erase the sent history or make a node uncarded. Show that warning and leave the note deleted. The saved counts work while Anki is offline and must not claim live presence. Pairing, reconciliation and sending retain their existing destination checks.

Legacy hand-written cards can lack a source snapshot, and their `statementHash` can describe card text rather than a graph statement. Count them when their exact node ID matches, but label the source comparison "not recorded". Do not infer a changed statement from their hash. Manual pseudo-IDs are not graph nodes and belong in card history, not the graph picker.

## Node states and precedence

Keep a base state and source warnings separate in the backend response. The UI shows one primary label plus counts and any additional warnings. This avoids losing a waiting draft behind a sent badge.

The base state uses these rules in order:

1. An explicit dismissal for the current statement hash gives `dismissed` when there are no waiting cards and no current or unknown-source sent cards for the paired destination. Stale sent history does not defeat a new dismissal.
2. Otherwise, at least one sent card for the paired destination gives `sent`.
3. Otherwise, at least one waiting card gives `drafts waiting`.
4. Otherwise, use `no cards`.

Sent-elsewhere cards do not change the base state. If both sent and waiting cards exist, show "Sent" with both counts and a route to review the waiting cards. A legacy unsnapshotted card counts under the same rules and retains its "source not recorded" warning.

For source warnings, consider non-dropped waiting cards, sent cards for the paired destination, and the saved dismissal. These are the relevant coverage records. A record is current when its trusted source hash matches the graph statement. A legacy card without a comparable snapshot has unknown source currency.

| Primary label | Rule and behavior |
|---|---|
| No cards | Base state is `no cards`, with no source warning taking precedence. Selectable and eligible for backfill. |
| Drafts waiting | Base state is `drafts waiting`. Show drafts, approvals, failures and unresolved deliveries in the count or details. Unresolved deliveries block more generation for this node. |
| Sent | Base state is `sent`. Grey the row but allow an explicit request for another angle unless a current dismissal, unresolved delivery or pending generation blocks it. |
| Dismissed | A current explicit dismissal has no waiting or current/unknown-source paired sent cards taking precedence. Stale sent counts remain visible. Unticked and excluded from backfill. Offer "Restore". |
| Source changed | The node exists, relevant records contain at least one trusted old hash, and none is current or of unknown currency. Show the base state and historical counts alongside the warning. Exclude it from ordinary backfill. |
| Source missing | A generated card with a saved source snapshot or a dismissal references an ID absent from the returned proposition snapshot. This does not prove deletion; the host may return incomplete data. Show it in a separate historical-source section with that caveat. It cannot be selected for generation. Untracked manual cards stay in card history rather than creating guessed graph rows. |

Missing takes precedence over changed. Changed takes precedence over the base label. If a node has current coverage as well as stale cards, show its base label and an "older-source cards" count instead of leaving it permanently in "Source changed". Unknown-currency cards prevent an assertion that all coverage is stale, but keep their warning visible. Dropped-only history never causes a changed-source warning.

Sent-elsewhere cards show their historical source information in card details. They do not by themselves make the current destination's node "Source changed". A matching node can therefore be "No cards" with a "sent to another profile" warning. Backfill then needs the normal explicit model confirmation and later send approval.

A writer skip with zero cards remains `no cards`, with its skip reason visible. Do not turn a model judgment into a user dismissal. A pending generation also does not count as coverage. Show "Generating" as activity, exclude its targets from bulk selection and prevent a second generation for those targets.

Source warnings do not rewrite cards or change existing delivery approvals. Changed-source cards remain reviewable under the existing approval and send rules. Generating another angle is an explicit action from "All nodes", with the old cards included in writer context.

## Dismissal data and actions

Dismissal belongs to a node, not to a delivery card. Do not add `dismissed` to the card delivery-status enum. Add a validated collection to the single atomic state snapshot with one record per node containing `nodeId`, `statementHash` and `dismissedAt`. The statement hash comes from the backend's current graph, not arbitrary frontend text.

Dismissals apply across sessions and Anki profiles for this plugin installation. "Don't card this" means the user does not want a card for this statement. It expires when the statement changes. Keep the old record so a later changed or missing source remains explainable. Re-dismissing the current statement replaces that node's previous record. "Restore" removes the record without creating a card.

The action submits the expected node ID and source hash. Inside the existing single-writer fence, reload the graph and state, reject missing or changed targets, validate the request and save atomically. Reject duplicate or malformed records during load rather than resetting the file. Use merged 0.4.0 schema 3 as the baseline and choose the next schema version at implementation time. Migrate that format and every already-supported older format with an empty dismissal collection, preserving settings, flags, generations and card identities. Unknown newer schemas remain refused.

For generations started with backfill targets, persist those target IDs in the existing generation record before any model call. Preserve them through restart and retry; absence on pre-0.5 generations means all targets were explicit requests. This is selection intent for the existing pipeline, not a second coverage ledger.

Do not dismiss a node while it has any non-dropped unsent card, an unresolved delivery, or pending generation work that can still create drafts. Ask the user to review or drop its drafts, or cancel and settle its generation first. A node with current or unknown-source sent coverage does not need dismissal. A node with only stale sent history may be dismissed for its new statement without touching those notes. A restored or expired dismissal never automatically starts generation.

A current dismissal is an independent selection guard in both views, regardless of the primary label or paired destination. Always show its dismissal warning and "Restore" action, even when re-pairing makes the primary label "Sent". It requires "Restore" before explicit selection or generation. Recheck this in backend preflight and confirmation, not only in checkbox code. Dismiss, restore, pairing changes and coverage changes relevant to selected targets invalidate a displayed estimate. Bind these inputs into preflight confirmation alongside the existing writer input so an old confirmation cannot bypass a newer dismissal.

## Picker and session flow

The v0.6.1 native `PluginKnowledgePickerProps` exposes only `value`, `onChange` and `disabled`. It cannot filter its rows or accept coverage labels. See LearnHarness `src/core/plugin-ui.ts:28-32` and `docs/plugin-api/plugin-ui.md:470-506`.

Use a plugin-owned DOM list for the coverage-aware picker. Reuse the session node-row and selection patterns from the final 0.4.0 implementation. Do not modify the host, inspect its widget DOM or silently strip IDs after a native picker reports them. Keep the existing model picker, settings, estimate, generation activity and card review components.

The graph-wide picker has:

- "All nodes" and "No cards" views, plus a name/statement search box.
- Each row's name, statement, primary coverage label and relevant counts or warnings. Use text and subdued styling, not color alone.
- "Select all uncarded" for the visible search/scope, with an exact node count and a maximum card count based on the configured cap. A maximum is not a generation quota. Keep the existing 1,000-node generation limit in both views and for individual selection. If a bulk action would exceed it, leave the selection unchanged and show the eligible count, the 1,000-node limit and an instruction to narrow the search or scope. Apply the same rule to automatic flagged-default updates on open and refresh: do not add defaults if they would exceed the limit, and show the same count and narrowing guidance. Do not silently truncate or raise the backend limit.
- "Clear selection", a selected-node summary and the existing "Estimate generation" action. No nodes are ticked by default in the graph-wide picker.
- "Don't card this" for eligible nodes and "Restore" for current dismissals. Missing-source history has no generation checkbox.

"No cards" includes only existing proposition rows whose primary label is `no cards`, with no pending generation or unresolved delivery. It excludes current dismissals, changed sources, missing sources, waiting drafts and sent coverage. Dropped-only nodes are eligible again. Sent-elsewhere nodes are eligible with a visible warning. Both the filter and bulk action use the same projection and eligibility predicate.

The session view keeps its 0.4.0 scope and ordering. Flagged nodes stay the default explicit request even if they already have cards. Extend that rule to exclude current dismissals and targets blocked by unresolved delivery or generation. A changed-source flagged node remains visible and may be explicitly selected with its warning. "Select all uncarded" uses the same predicate as the graph-wide picker. Unflagged sent nodes remain unticked when seen in a later session.

Preserve per-target selection intent through the first preflight and confirmation: "Select all uncarded" selects for backfill; individual selection and the session's flagged defaults are explicit requests. Pass that intent with the target IDs into the existing preflight and bind it into confirmation. The backend rechecks the shared no-cards predicate for backfill targets at both steps. If coverage changes before the first estimate, reject newly ineligible backfill targets and require explicit reselection for another angle; never silently promote backfill to an explicit request. Dismissal and unresolved-delivery/generation guards apply to either intent. "Estimate retry" must retain the saved backfill intent for unfinished targets and recheck it in retry preflight and confirmation. A failed backfill target that gains a draft before retry is no longer eligible; reject it and require explicit reselection rather than estimating another angle. Newly created retry generations retain the same backfill IDs for their remaining targets.

Filter, search or scope changes remove hidden selections and invalidate the estimate. Show the revised selected count. Refresh preserves explicit choices for still-visible, eligible nodes and does not retick nodes the user cleared. Source statement changes invalidate preflight even if the node ID stays selected. Backend confirmation must revalidate current eligibility and coverage inputs before starting work.

API v1 has no graph-changed event. Refresh on opening the view, explicit "Refresh graph", the existing session polling/resync points, and local generation, review, delivery or dismissal changes. Use the existing lifetime and revision guards so stale asynchronous responses cannot restore an old selection or estimate. Coverage-only reads must not require a selected model, a model catalog lookup or a live Anki connection.

## Implementation boundary

Using the merged 0.4.0 baseline, extract one pure coverage projection used by backend snapshots, session counts, filters and bulk selection. Avoid separate interpretations of "uncarded" in the session and manual views. Add dismissal commands behind the same writer fence used by generation and delivery. The frontend consumes the projection; it does not infer success from network errors or maintain its own durable counts.

Expected integration points are `src/anki/state.ts`, `src/backend.ts`, the final session service and selection helpers, `src/drafting-ui.ts`, and the existing frontend view wiring. Re-read those files after the merge. This PR deliberately changes none of them, bumps no package or manifest version, and adds no migration or production tests.

## Acceptance cases for implementation

These checks are required for the future implementation. They have not been run as coverage-plugin tests in this docs-only change.

| Case | Required result |
|---|---|
| Same proposition reencountered in a second session | Shares existing coverage by exact ID; unflagged sent node is unticked. |
| Identical text under a new ID after deletion | New node is uncarded; old history is missing. An ID-shaped alias does not transfer coverage. |
| Draft, approved, failed and sending cards | Count as waiting; sending warns and blocks more generation for that node. |
| Sent plus waiting cards | Primary base label is sent and both counts remain visible. |
| Dropped-only history or writer skip | No cards; skip reason is visible and no dismissal is invented. |
| Pending generation with no cards yet | No cards plus activity; absent from bulk selection and blocked from duplicate generation. |
| Same destination, different deck | Sent coverage remains. |
| Different or absent pairing | Sent-elsewhere warning; no false current-destination coverage. |
| Anki offline, active profile mismatch or deleted note | Saved history remains; no presence claim, resend or mutation. Existing delivery safety checks remain. |
| Statement changes, all relevant coverage stale | Source changed; old counts retained and ordinary backfill excludes the node. |
| Current cards plus stale cards | Current base label plus older-source count, not a permanent changed label. |
| Name, aliases, provenance or chains change alone | No statement-hash warning; actual writer input still invalidates an old estimate. |
| Legacy card without source snapshot | Counts by exact ID, with source comparison not recorded. No false statement-hash warning. |
| Dismiss, reopen, restart, switch session/profile | Current dismissal persists, remains unticked and makes no Anki call. |
| Sent to B, dismiss while A is paired, then pair B | Sent counts return, but dismissal and Restore stay visible; selection and generation remain blocked until restored. |
| Restore or change a dismissed statement | Restore returns to derived coverage; statement change shows attention. Neither starts generation. |
| Dismiss new statement with only stale sent history | Dismissed takes precedence over historical sent counts; notes and counts remain intact. |
| Dismiss while drafts or generation exist | Reject without dropping drafts or losing later worker results. |
| Corrupt, duplicate or newer-schema dismissal data | Refuse safely; preserve the original state file. |
| Migration from every supported old schema | Preserve all card IDs, flags, generation recovery data, settings and pairing. |
| Filter/search/scope changes, refresh and late responses | Visible selection and count agree; hidden nodes cannot be generated by an old estimate. |
| Pairing or dismissal changes after estimate | Old confirmation fails and requests a fresh estimate. |
| Bulk-selected uncarded node becomes sent before first estimate | Backfill intent survives; backend rejects the stale target instead of estimating another angle. Explicit reselection is required. |
| Failed backfill target gains a draft before retry, including after restart | Saved backfill intent survives. Retry estimate rejects the target; another angle requires explicit reselection. Legacy generations without backfill IDs remain explicit requests. |
| Exactly 1,000 eligible nodes selected | Existing estimate and confirmation flow accepts the node count. |
| Bulk action would select 1,001 eligible nodes | Selection stays unchanged; show 1,001 eligible, the 1,000-node limit and a narrowing instruction. No estimate or model call; individual selection cannot exceed the same limit. |
| Session open or refresh would auto-select more than 1,000 flagged defaults | Do not add the defaults. Keep the selection within the cap and show the eligible count and narrowing guidance, without silent truncation. |
| Graph facade reports a read failure | Keep last view stale and selection changes disabled; no missing-source relabeling, model call or state rewrite. |
| Successful snapshot omits a selected node after estimate | Mark it absent from this snapshot, not confirmed deleted; preserve history and reject generation. Empty/partial snapshots may be silent host read failures. |
| Coverage view without model selection or Anki | Labels and filter still work. |

Run unit and DOM tests for these rules, then verify the picker and session flow in scratch LearnHarness with isolated data. Use a stub worker before a real-model smoke test. Any Anki writes must use a throwaway profile. Keep these checks separate from the already-passing graph identity experiment and full card-quality validation, which remains deferred until before release. The earlier human spot-check is complete.
